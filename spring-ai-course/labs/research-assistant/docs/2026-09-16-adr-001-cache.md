# ADR-001: How we cache catalog data (2026-09-16)

Status: ACCEPTED
Author: Lena

## Context
The catalog API is too slow (840 ms p95). The same product data is read thousands of times per minute.
We run 4 to 12 instances.

## Options
1. Caffeine, a local in-memory cache in each instance.
   - Very fast, no network hop.
   - Each instance has its own copy: after a price change, instances disagree until their entries expire.
   - With 12 instances, the database is still hit 12 times for each product.
2. Redis, a shared cache for all instances.
   - One copy for all instances, so a price change can be evicted in one place.
   - Adds a network hop (about 1 ms in our data center).
   - The platform team can provide a single Redis node now. A replicated setup needs more time.

## Decision
We use **Redis** as a shared cache for product and price data.
- Time to live (TTL): **10 minutes** for product data.
- Prices are cached too, with the same TTL, and must be evicted when a price changes.
- We do NOT use Caffeine, because instances would show different prices after a change.

## Consequences
- We depend on Redis. If Redis is down, the service falls back to PostgreSQL (slower, but correct).
- The single Redis node is a known risk. To be reviewed after the sales week.
- We must build an eviction path for price changes (owner: Sam).
